A thorough `.dockerignore` for Node.js projects. Keeping irrelevant files out of the build context speeds up `docker build` (less data sent to the daemon) and prevents secrets, test artifacts, and local tooling configs from accidentally ending up in the image.

## How it works

Docker reads `.dockerignore` before evaluating any `COPY` or `ADD` instruction. Patterns follow the same syntax as `.gitignore`: a leading `!` negates a rule, so `.env.*` combined with `!.env.example` excludes all `.env` variants but keeps the example file.

Because `node_modules` is excluded, the `COPY . .` in your Dockerfile won't bundle your host's `node_modules` into the image — the Dockerfile should run `npm ci` (or the equivalent) instead, installing a clean set of packages inside the container.

## Notes

- Adjust framework-specific output directories (`dist`, `.next`, `.nuxt`, etc.) to match your project.
- If your repo has multiple packages (monorepo), you may need to keep certain `node_modules` or `dist` folders — use negation patterns (e.g. `!packages/shared/dist`) carefully.
- Run `docker build --no-cache .` after updating `.dockerignore` to verify the context size reduction in the build output: `Sending build context to Docker daemon X MB`.
- Check what's currently included with: `docker build --dry-run .` (Docker Engine 23+) or by inspecting the build context size in the regular build output.
